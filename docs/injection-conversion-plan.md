# 补丁注入式改造规划（2026-09-25 拍板）

目标：所有补丁（EFB 汉化、座舱悬浮提示汉化、后续新增项）统一为**注入式**——把汉化文件直接写入
机模厂商包原位，逐文件备份、可随时还原，替代跨包遮蔽 overlay。

背景：座舱提示汉化的实机验证证明，部分机模（PMDG 附件相对包含、TFDi 包内行为解析）的文件加载
**根本不经过跨包 VFS**，遮蔽通路对它们无效；注入是唯一全机模可靠的方式。统一为注入后架构单一、
维护面收敛。

## 设计要点

1. **备份台账（统一模块）**：逐文件首触备份原件 + manifest（original sha、injected sha、
   backedUpAt、机模/包名），首触记录、永不覆盖。现有 fill-vendor.mjs 与 inject-hardcoded.mjs
   各有一套，P1 统一为共享模块 `lib-backup.mjs`。
2. **厂商更新检测**：注入前哈希三态闸（base=未动 / injectedSha=已注入 / 其他=厂商更新，拒绝并
   提示重提取）。客户端安装与重装同样落台账；机模更新后客户端需能提示"汉化需重装"。
3. **客户端安装动作**：新增「注入安装」类型——ZIP 内含 payload + manifest（目标包名、相对路径、
   base 哈希），客户端写入厂商包前先做原文件备份入台账；还原 = 从台账备份字节级恢复 + 删除新增
   文件（仅当哈希仍等于注入产物，用户改动过的文件保留并提示）。
4. **水印接入**：注入产物沿用六层水印构建管线；layout/manifest 属厂商文件不可动，水印落在
   注入文件内容层（L1/L2/L5）。
5. **EFB 特有风险**：EFB 注入 = 把引擎/词典/字体写入厂商包 html_ui；单机模体积大（字体约 45MB）；
   厂商更新会整体覆盖，依赖哈希检测 + 客户端重装指引；与遮蔽方案相比失去"删包即还原"的清洁性，
   还原完全依赖台账——台账可靠性是注入式架构的生命线。
6. **iFly 座舱**：建议转为注入统一架构（其模型级行为文件经 VFS，遮蔽也可用，但架构统一优先）。

## 阶段

- **P0（已达成）**：座舱 locPak/XML 注入上线（7 机模实机验收通过）。
- **P1**：统一备份台账模块 + inject/fill 工具合并。
- **P2**：EFB 注入转换试点（建议 Fenix——厂商包结构最简单、实机验证周期最短）。
- **P3**：客户端「注入安装」动作 + 水印接入 + 还原台账。
- **P4**：全机模 EFB 铺开 + iFly 座舱遮蔽转注入。

## 红线

- 备份原件永不覆盖；还原必须字节级。
- 厂商更新覆盖注入内容后：检测→提示重装，绝不静默失败。
- 发布前重建 release 形态产物（如 Fenix EFB 当前部署为 --diag 构建，发布前必须重跑不带 --diag 的构建）。
